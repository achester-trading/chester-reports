## The answer: T1 now, the Doctrine this weekend, in parallel

They use different resources. T1 is session time; the Doctrine is Ari's attention. T1 runs on the *proposed* values in config and the Doctrine's rulings are config values, so nothing in T1 waits on the sitting. The one ordering rule: the Doctrine's rulings on the regime mapping and the risk limits touch live enforcement, so they are applied to `main` by a short session (D-1) before T1 merges, and the T1 branch rebases onto them.

Doing the Doctrine first would cost two days of session time for nothing; doing T1 first and skipping the weekend sitting would leave eight proposed values running unratified for another month.

## Principles of the order

1. **Reports before plumbing before feeds before depth before the big orders.** The stack (T1–T3, 6d) changes what Ari reads every day, so it goes first; the cloud migration takes the laptop out of the loop; 6b brings the intraday feeds; 6e/6f deepen the data; the Enterprise Layer and signal-triage work orders are placed by Audit #4 and run after.
2. **One session task at a time; one chat decision at a time.** Never the same paste to two sessions.
3. **Two deploy freezes:** the evening before Audit #4 (Tue 13 Oct 23:30) and before the 1 Nov Monthly (Thu 29 Oct 23:30). Code on branches continues; nothing lands on the box.
4. **Sign-offs happen at sittings, not in passing.** The Doctrine monthly ratifies values; Audit #4 places work orders.
