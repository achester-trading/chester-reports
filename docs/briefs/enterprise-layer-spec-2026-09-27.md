# I. ORGANIZING PRINCIPLE

The architecture should approximately follow:

**Trading engines optimize decisions within defined horizons.  
Research optimizes understanding across horizons.  
Independent Evaluation determines what actually worked.  
Risk optimizes survival and portfolio coherence.  
Red Team optimizes skepticism.  
Doctrine challenges structural assumptions.  
Architecture optimizes the machine.  
Orchestration preserves coherence without destroying independence.**

Critically assess whether this formulation is useful and revise it if necessary.

# II. SIX ENTERPRISE AGENTS + ORCHESTRATION

My current preferred architecture is six enterprise agents/functions plus a central orchestration layer.

Do not assume six is automatically correct.

Critically evaluate whether responsibilities should be combined, divided, automated or removed.

# III. CENTRAL ORCHESTRATION LAYER — NOT A SEVENTH CIO AGENT

Do not initially build a separate autonomous Meta-Allocator / CIO Agent.

Instead use a governed orchestration layer.

Its role is to:

- collect outputs
- preserve disagreement
- enforce interfaces
- maintain horizon-separated views
- route information
- apply explicit decision rules
- surface conflicts
- produce coherent decision packages
- ensure required risk/adversarial checks occurred

It should **not erase disagreement**.

Its objective is coherence, not consensus.

Avoid creating a final LLM that simply overrides all six independent functions.

# V. CROSS-HORIZON STATE

Maintain separate beliefs across horizons.

For example:

| Horizon | Possible state |
|---|---|
| Structural | Bullish |
| 1–3 months | Bullish |
| 1–4 weeks | Sideways/Bullish |
| 1–5 days | Neutral |
| Intraday | Bearish |
| Immediate | Sell-the-rip |

Do not force these views into a single market call.

A short-horizon trade contrary to a long-term view may be completely rational.

The enterprise framework should record whether a trade is:

- aligned with
- neutral to
- counter to

the higher-horizon view.

Then empirically test whether this relationship affects performance.

# IX. EPISTEMIC INDEPENDENCE

Different agents should not simply be different names attached to the same reasoning process.

Where practical, preserve independence.

Examples:

- Research proposes a hypothesis before seeing the Red Team conclusion.
- Red Team may initially inspect evidence without seeing Research's persuasive narrative.
- Enterprise Risk should evaluate portfolio exposure without being incentivized to support the originating trade.
- Independent Evaluation must judge the original timestamped forecast, not a rewritten post-event explanation.

Use blind or partially blinded review when useful.

Do not treat five agents repeating the same underlying evidence as five independent confirmations.

# XI. FALSIFIABILITY

Every material hypothesis should specify:

- what we believe
- why
- horizon
- expected observable consequences
- conditions under which it should work
- evidence that would weaken it
- evidence that would invalidate it

This should be stored before outcomes occur.

Independent Evaluation should grade the original hypothesis.

# XII. CONTROLLED LEARNING

Do not permit uncontrolled production self-modification.

Use:

**OBSERVATION  
→ HYPOTHESIS  
→ RESEARCH  
→ TEST  
→ ADVERSARIAL REVIEW  
→ INDEPENDENT VALIDATION  
→ SHADOW DEPLOYMENT  
→ CHAMPION / CHALLENGER  
→ HUMAN APPROVAL WHERE MATERIAL  
→ PRODUCTION  
→ MONITORING  
→ ROLLBACK**

A rule change remains an experiment until improvement is demonstrated.

# XIII. POINT-IN-TIME INTEGRITY

Historical evaluation must use only information genuinely available at the relevant timestamp.

Protect against:

- look-ahead bias
- revised economic data
- survivorship bias
- future-derived regime labels
- post-event narrative contamination
- retroactive signal definitions

Use vintage-aware data where necessary.
